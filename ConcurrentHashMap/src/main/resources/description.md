The core concept behind lock striping is dividing the shared data structure into `N` separate partitions (segments) and assigning a distinct lock to each partition.

If Thread A wants to write to Segment 1, and Thread B wants to write to Segment 5, they can do so simultaneously without blocking each other. This drastically increases throughput compared to a `Collections.synchronizedMap` or `Hashtable`, which uses a single global lock and forces all threads to queue up regardless of which key they are accessing.

## Key SDE II Design Discussion Points

* **The Global Operation Bottleneck (`size()`):** Lock striping makes localized operations (`put`, `get`) extremely fast, but it makes global operations terribly complex. In the `size()` method above, we iterate through the segments. However, because we do not lock *all* segments simultaneously, Thread 1 could add an item to Segment 4 while we are counting Segment 1. Thus, `size()` in a striped map is only an *eventually consistent approximation*, not an absolute guarantee. Locking all segments to get a perfectly accurate size would defeat the entire purpose of concurrency.
* **The Negative Index Hash Trap:** In `getSegmentIndex()`, using `Math.abs(key.hashCode()) % concurrencyLevel` is a common junior mistake. In Java, `Math.abs(Integer.MIN_VALUE)` evaluates to `Integer.MIN_VALUE` (a negative number due to two's complement overflow). Using `(hash & 0x7FFFFFFF)` explicitly strips the sign bit, guaranteeing a positive index and preventing an `ArrayIndexOutOfBoundsException`.
* **Java 7 vs Java 8 `ConcurrentHashMap`:** The code above is exactly how Java 7 implemented `ConcurrentHashMap` (with a default concurrency level of 16). Java 8 abandoned the `Segment` array entirely. Instead, Java 8 locks the *first node* of the individual bucket (the head of the linked list) using synchronized blocks and Compare-And-Swap (CAS) operations. This effectively made the concurrency level equal to the map's total capacity, increasing throughput even further.
